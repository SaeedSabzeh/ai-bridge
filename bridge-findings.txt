Delegating work from Claude Code to ChatGPT

Three ways to use the same bridge

- Delegated task. Claude assigns ChatGPT work to complete, such as editing
  translations or verifying an experiment. ChatGPT handles the assignment and
  returns a result to the Claude session that launched it.
- Automatic question. Either assistant asks for advice or a second opinion.
  The bridge runs the peer's subscription CLI and returns a reply. This is
  the existing automatic ask_peer flow.
- Manual question. Either assistant leaves a question in the shared inbox
  for an active peer session to answer. This is the existing manual flow.

Use one mailbox and conversation view for all three. A delegated task has its
own work scope and completion report. The existing question tools still serve
quick consultations and back-and-forth discussions.

How the handoff should work

Claude assigns ChatGPT an outcome, names the files it can use, and specifies
what it may do. ChatGPT takes the task from there. It opens the assigned files,
works through the task, and returns one result Claude can act on. The result
includes what it inspected, what it changed or checked, what it found, and
anything it could not verify. Claude reviews the result and continues its work.

The existing mailbox can carry the assignment, status, and final report. The
missing capability is a worker that can access the assigned files and perform
the authorized work. Claude should be able to pass paths directly without
copying every excerpt into the prompt or walking ChatGPT through each step.

Returning the result to the originating Claude session

When Claude launches a delegated task, associate the request with the calling
Claude session and return a request ID. ChatGPT works in a separate worker.
The bridge saves the completion report and any output references before
delivering them. The request ID tracks one execution. A task ID groups related
exchanges. The Claude session association determines where the result goes.

The simplest first version is a Claude-side caller that submits the task and
waits or polls the same request ID until completion, then returns the report
through its normal result channel. That gives the initiating Claude session
the result without requiring Saeed to check the panel or ask again. If Claude
can keep working while the caller waits, it can pick up the result when it is
ready. Automatic delivery after the caller has returned would need a Claude
client integration that can route completion back to the right session. The
current panel displays mailbox updates, and the current MCP tools retrieve
replies by request ID.

Keep completed results available for retrieval if the session disconnects.
Return failures and blocked outcomes through the same path so Claude can
decide how to proceed. Test by starting work from two Claude sessions, having
the tasks finish out of order, and checking that each session receives only
its own result. Also test retrieval after a disconnect without launching the
same job again.

What you want

Claude should be able to hand ChatGPT a concrete assignment such as “Polish the
Italian translations in locales/it.json. Make the copy natural and catchy, and
preserve the translation keys and placeholders.” ChatGPT should do the editing
work and return a short report Claude can use to finish the job.

What the bridge does today

Claude's ask_peer tool sends a question and supplied context. The bridge runs
Codex through the signed-in ChatGPT subscription and returns a text reply under
the same request ID. The automatic worker runs with editing tools disabled. The
current translation skill asks ChatGPT for suggestions and leaves Claude to
decide which ones to use and make each edit. The mailbox and conversation panels
already support the handoff and return of results.

A first version of delegated editing

1. Claude submits an edit task with the project folder, the exact target file,
   the goal, and any relevant context such as source strings and tone. Start
   with one existing UTF-8 text file per task.
2. The bridge snapshots the named file and sends its contents to ChatGPT.
   ChatGPT returns machine-readable edits plus a short summary, including an
   explicit no-change result if the file already reads well.
3. The bridge validates the edits against the snapshot. For JSON locales, it
   can check that the result parses, the keys and structure match, and each
   string keeps its protected placeholders. Preserve the original line endings
   and UTF-8 encoding details. The target comes from Claude's request. The
   model's reply supplies only the edits and report.
4. Claude receives the prepared edit and summary through the existing request
   ID. A separate apply step can write the validated result in one operation.
   Claude can call it in the same workflow, review the diff, and run the
   project's checks without redoing the wording. Compare the current file with
   both the snapshot and the prepared result. If the result is already on disk,
   report success without writing again. If the file matches neither version,
   report a conflict so Claude can review it.

For example, Claude would receive “Updated seven Italian strings. Shortened the
checkout buttons and made the welcome copy more conversational. JSON parsed and
all keys and placeholders were preserved.” The report should distinguish edits
that are ready to apply from edits already written, and list only checks that
actually ran.

Claude's design review pointed out that a crash after writing can leave the
mailbox without a completion record. Checking for the prepared result lets
Claude retry in that case. A hash check followed by a file replacement still
has a race with another editor. If the bridge cannot coordinate the write with
the editor, Claude can apply the prepared result through its normal edit tool.

Acceptance tests should cover a successful apply, a repeated apply, a target
changed while ChatGPT was working, invalid JSON, a dropped placeholder, and a
Windows CRLF file.

Kaggle example — delegate the experiment review

Claude runs the experiments and saves the evidence. It gives ChatGPT the claim
to review, the paths to the saved findings, scores, and relevant code, and a
scope for verification. ChatGPT opens the evidence itself, checks whether the
baseline and new run used comparable folds and metrics, and looks for leakage
or a gain driven by one fold. If the assignment authorizes a check such as
recalculating scores from saved predictions, ChatGPT runs it and records what
the check showed. A full rerun is a separate check that needs the data,
environment, and compute.

Example request

“Independently review whether feature X improved our model. Read findings.md,
results/fold_scores.csv, and src/validation.py. Recalculate the reported gain,
check whether the folds match, and look for leakage. Return a verdict with
file references, checks performed, uncertainties, and the next test you would
run. Keep the experiment files read-only.”

The current bridge can already deliver a second opinion when Claude includes
the evidence in the request. The subagent version would let ChatGPT gather
the assigned evidence from those paths and complete the verification on its
own. Claude can use the same task ID to send follow-up results and ask whether
they change the verdict.

When to ask each other — web research, November 8, 2026

The comparisons below cover specific models, reasoning settings, and tools.
Use them as starting points for routing work. The published scores were
measured outside this bridge. OpenAI's official documentation lists GPT-6.1
Sol and GPT-6 Astra for Codex, with access depending on the account and client.
https://learn.chatgpt.com/docs/models

Claude to ChatGPT / Codex

- Audit a Kaggle run or reproduce a data result. Give Codex the predictions,
  metric code, split definitions, and experiment logs. Ask for recalculated
  scores and specific discrepancies. On Terminal-Bench-Science with the same
  agent setup, GPT-6 Astra scored 62.9%, GPT-6.1 Sol 52.9%, and Claude Opus
  5.5 47.1%. The Sol–Opus gap has overlapping reported error ranges. These
  are scientific workflow tasks, so using Codex for Kaggle evidence review
  is an inference from the benchmark.
  https://vals-ai.com/benchmarks/terminal-bench-science

- Inspect an unfamiliar binary or firmware behavior. For authorized work, give
  Codex the sample and ask it to document what it can reproduce. On the
  software reverse-engineering benchmark SRE Bench, Astra scored 56.9%,
  6.1 Sol 50.8%, and Opus 5.5 33.6% in the published configurations.
  https://vals-ai.com/benchmarks/srebench

ChatGPT / Codex to Claude

- Fix a front-end bug reported with a screenshot. Give Claude the reproduction,
  image, and relevant repository. On Vals' SWE-bench Multimodal runs with the
  same agent setup, Opus 5.5 solved 70.2% of issues, compared with 43.5% for
  GPT-6.1 Sol and 43.3% for Astra.
  https://www.vals-ai.com/benchmarks/swebench-multimodal

- Take a difficult repository task or review a professional deliverable.
  Terminal-Bench 4.0 reported 64.8% for Opus 5.5 in Claude Code versus 58.2%
  for both Astra and 6.1 Sol in Codex, all at max effort. Claude Opus 5.5 also
  led GDPval-AA v2.1, which evaluates finished work such as reports, slides,
  and spreadsheets. This makes Claude a good candidate for a multi-step repo
  task or for checking whether a report meets its brief and uses the evidence.
  https://www.tbench.ai/
  https://artificialanalysis.ai/evaluations/gdpval-aa

- Rank possible Kaggle experiments before spending compute. In a preprint
  covering 288 ideas across eight MLE-bench tasks, Opus 5.5 explained more of
  the observed variation than Astra (R-squared 0.49 vs. 0.38). Use this as a
  signal for prioritizing ideas. Confirm the winner by running the experiment.
  https://arxiv.org/abs/2610.22599

Translation and independent review

- For natural, catchy website translations, ask the other assistant for a
  pass when the wording matters. Compare a small blind sample for the actual
  language, audience, and UI. Score naturalness, meaning, and fit, and validate
  keys and placeholders mechanically. Public translation benchmarks use
  automated scores by language pair. They give limited evidence about which
  model writes the best copy for a particular site.
  https://benchmark.algebras.ai/?pair=EN%E2%86%92ZH&sort=fluency_desc

- Delegate when the peer can return a concrete diff, verified score, or test
  result. Use an automatic question for a quick critique and a manual question
  when you want the other active session's project context. A study of 50 web
  app builds found a significant quality gain in only one of four comparisons
  between agent teams and single agents. That study did not test this bridge.
  https://vals-ai.com/blogs/multi-agent-vibe-code-bench

A leader that assigns work using benchmarks

For a complex job, the lead session breaks the goal into steps and marks
which outputs each step depends on. The leader assigns each step either to
itself or to the other assistant using the closest relevant benchmark. It
owns the overall plan, reviews the returned work, and can revise later steps
once it sees the results. Benchmark rankings belong to particular models and
settings, so the leader compares the models actually available to the bridge.

How the leader chooses

1. Define the step's deliverable and how it will be checked. Identify the
   required inputs, tools, and permissions. Start a step when its inputs are
   ready. Independent steps can run concurrently where the bridge supports it.
2. Pick the benchmark that most closely matches the work. Use screenshot-based
   bug-fix results for a visual repository issue, for example. Give the most
   weight to direct comparisons with similar tools, effort, and evaluation
   conditions. Use clear differences as routing signals. Treat small gaps and
   results from loosely related benchmarks as weak evidence.
3. Assign a step to the stronger eligible model when the evidence is clear
   and the task has a concrete handoff. When scores are close or the match is
   weak, keep tightly linked steps together with the assistant that has the
   working context. Use a representative sample to compare repeat tasks such
   as translation. Record which model ran and whether the output passed, so
   results on Saeed's work can refine the benchmark-based choice.
4. Send the worker the goal, input paths, allowed actions, and acceptance
   check. The worker returns its artifact and report to the originating lead
   session. The leader checks that output before any dependent step uses it.

Example. Claude keeps the Kaggle project context, prioritizes candidate
experiments, and runs them. When results are saved, it delegates an audit of
the scores and validation logic to Codex. The evidence and verdict return to
that Claude session. If Codex finds a mismatch, Claude fixes the comparison
and reruns it before deciding what to submit. In a website job, the same
leader could keep a screenshot-based UI fix with Claude and assign a separate
translation pass using the winner of a sample from the site's actual strings.

Planning the steps and changing who does them are separate decisions. In a
controlled study, coordinating agents helped on a parallelizable analysis
benchmark, while every tested multi-agent setup scored worse on the study's
strictly sequential planning benchmark. This supports using the benchmark
router at clean handoffs and retaining one owner across tightly coupled steps.
https://arxiv.org/abs/2512.08296
https://www.anthropic.com/research/building-effective-agents

Choosing the exact Claude model — web research, November 8, 2026

Once the leader chooses Claude for a step, it selects the model version and
effort as part of the assignment. These are proposed starting choices. The
benchmark results below come from the cited test configurations.

- Claude Haiku 5.5 (claude-haiku-5-5), medium effort. Use for routine form
  fields with a clear source and known schema, such as copying a supplied
  address into labeled fields. Also use for straightforward extraction,
  classification, and short summaries. In a small direct comparison, Haiku
  and Sonnet both answered all six questions from two PDFs correctly, with
  one run per question and lower API charges for Haiku. That tests document
  lookup. Validate actual form filling on examples from the intended workflow.
  https://platform.claude.com/docs/en/models/overview
  https://creatos.io/tests/claude-haiku-5-5-vs-sonnet-5-5-documents

- Claude Sonnet 5.5 (claude-sonnet-5-5), high effort. Use when the form has
  branching screens, messy source material, or fields that need ordinary
  interpretation. Also use for a scoped repo change or a document draft with
  a clear brief. Anthropic reported 83.9% for Sonnet versus 72.4% for Haiku on
  the OSWorld 2.1 offline desktop subset, using partial credit. On Artificial
  Analysis's GDPval-AA v2.1, Sonnet reached 1838 Elo at max effort versus
  Opus's 1866 at max, with overlapping published intervals.
  https://www.anthropic.com/claude-haiku-5-5
  https://artificialanalysis.ai/evaluations/gdpval-aa

- Claude Opus 5.5 (claude-opus-5-5), high effort to start. Use when the task
  requires reconciling conflicting records, interpreting interdependent rules,
  debugging across a repository, or making a decision that needs sustained
  judgment. On Vals' screenshot-based SWE-bench Multimodal runs, Opus solved
  70.2%, Sonnet 58.3%, and Haiku 44.0%. That is direct evidence for visual
  software fixes and indirect evidence for deciding how to handle hard forms.
  https://www.vals-ai.com/benchmarks/swebench-multimodal

- Claude Fable 5.1 (claude-fable-5-1). Consider only when the account exposes
  that exact model and a relevant evaluation or failed Opus attempt justifies
  the extra work. Opus beat Fable on both of the cited Vals screenshot and
  Artificial Analysis work-product tests, so those tasks already favor Opus.
  https://platform.claude.com/docs/en/models/overview
  https://code.claude.com/docs/en/model-config
  https://www.vals-ai.com/benchmarks/swebench-multimodal
  https://artificialanalysis.ai/evaluations/gdpval-aa

For forms, pass the source and fields to the worker. Require the proposed
value and its source for each field, plus a list of missing or conflicting
items. Check the draft against the source, required fields, formats, and
allowed values. Use the first model that meets the accuracy requirement on
representative examples. Route ambiguous cases to the appropriate stronger
model or ask for the missing information. Any screen interaction needs a
worker with the appropriate tool and scope.

The proposed bridge would pass the full model ID with Claude Code's --model
and set --effort on the worker. Log the requested model, the model that ran
when available, the effort, elapsed time, validation result, and reason for
any fallback. The current bridge does not pass per-request model or effort
settings. Manual questions still go to the active peer session.
https://code.claude.com/docs/en/cli-reference

How to make it practical

1. Try one real job with the bridge as it exists. Start in the Claude session
   that owns a finished Kaggle run. Give it this instruction.

   “Use the local AI Bridge to ask ChatGPT for an independent audit of this
   run. Share the baseline and candidate per-fold scores, split definition,
   and metric code. Ask it to check the gain and find any unfair comparison.
   Poll the same request ID, then verify its findings against the saved run.
   Bring the verdict back here with the evidence and the next action.”

   Claude supplies the relevant excerpts and runs any project checks itself
   in this pilot. Record whether the peer found a confirmed issue, how long
   the handoff took, and how much rework the result needed. This gives you a
   comparison before changing the bridge.

2. Build one delegated review end to end. Keep the existing automatic and
   manual question tools. Add a separate delegated-task tool that accepts the
   goal, project root, named inputs, allowed action, expected result, and an
   exact model and effort when specified. Start with read-only review of
   named files. Let the bridge resolve and snapshot the inputs and give the
   worker access only to those copies. Add one bounded verification action,
   such as recalculating a known metric from saved predictions. Save the
   report, input references, actual model if available, checks, and outcome
   under the existing request ID.

3. Make it feel native in Claude. Start with a Claude Code subagent wrapper
   that submits the job, tracks the request ID, and returns the result through
   Claude's subagent mechanism. Claude Code documents delivery of background
   subagent results to the calling conversation. Verify that the installed
   client exposes the bridge MCP tools to that wrapper. Keep the saved result
   retrievable if the calling session disconnects. This gives the leader a
   single assignment and completion to track.
   https://code.claude.com/docs/en/sub-agents

4. Add edits once delivery is reliable. Use the translation example first.
   ChatGPT returns a prepared diff and summary for one named file. Claude
   reviews and applies it with the original-file check described above.
   Add more work types when a real job calls for them.

Keep the routing rules short at first. The lead picks a provider, model, and
effort from the findings, and records one reason. Example choices include
Haiku 5.5 medium for known form fields, Sonnet 5.5 high for scoped work that
needs interpretation, Opus 5.5 high for conflicting evidence, and Codex for
a separate experimental audit. Use verified results on repeated tasks to
adjust these defaults. A general scheduler can wait until a workflow needs it.

The first release is ready when Claude can delegate a real read-only audit,
continue other work if it chooses, receive the report in the same session,
and verify its evidence. Exercise two originating sessions with out-of-order
completions, an unavailable model, a disconnected session, and the existing
automatic and manual question flows.

Reliability work before delegated tasks

1. Make failures understandable. Return a stable error category, a short
   explanation, and a next step. For example, “Codex isn't signed in. Run
   codex login, then retry.” For a usage limit, show the period and reset time
   only when the provider reports them. Keep the CLI exit code and sanitized
   technical details available separately. The bridge already detects some
   setup and sign-in problems. Provider failures can still surface as raw text.

2. Make status accurate. Keep the existing stored states for compatibility.
   Show Waiting for a queued automatic request, Waiting in inbox for a manual
   question, and Working once a worker has claimed it. Show Answered, Failed,
   and Cancelled from the stored state. The Claude panel currently labels
   queued and running automatic requests as Thinking. A lost worker currently
   depends on an age check when the mailbox is read. Record enough worker
   liveness information to detect an unexpected exit and mark it Failed
   promptly. Keep the deadline as a fallback and preserve terminal states
   if a late result arrives. Manual inbox entries wait for an answer or cancel.

3. Make retries predictable. Allow at most one automatic retry for a known
   temporary failure when there is evidence the provider never accepted the
   request, or when the operation has a reliable idempotency guarantee.
   Sign-in problems, usage limits, and uncertain outcomes require a visible
   next step. Today a saved-session turn catches any BridgeError, forgets
   the session, and starts a fresh call. This can repeat a timed-out or
   otherwise unconfirmed request. Start a fresh session only for a clearly
   rejected resume, record the reason, and verify that the original turn
   never ran. Fetching status should never trigger a model call.

4. Remove fixed computer paths. The Python core already locates itself and
   the Codex installer locates Python. The Claude panel hard-codes both the
   bridge folder and Python executable. Use discovery plus one override file,
   bridge-config.json. Make the panel and both CLI launchers use the same
   resolved settings. Installed clients may still need their registration
   refreshed after a move. Make that a single reconnect step and test it
   from a moved directory with spaces.

5. Test failure paths. Extend the 24-test Python baseline. The current suite
   already covers a missing CLI, duplicate submission, and restart without
   replay. Add a worker killed after claiming a request, a provider unavailable
   before and after request acceptance, a confirmed invalid saved session, and
   two distinct requests submitted at once. Assert the visible state and next
   step, the number of provider attempts, and the absence of a duplicate call
   on recovery. Also exercise queued versus working in both conversation views.

6. Show what was shared. Add a details view for the submitted question,
   context, and prior exchanges the bridge actually included, with truncation
   marked. Show whether the provider session was resumed, started fresh,
   or rejected and replaced. A task ID or round number alone cannot tell you
   which happened. Label provider-retained conversation history separately
   from the exact content this bridge sent. Keep full context in an explicit
   local details view and give older requests an Unknown value when the
   mailbox lacks that information.

Local browser view for the conversation and worker activity

Extend the browser viewer already in codex_conversation.py. It serves a
read-only page on 127.0.0.1 with a session token and reads the existing
mailbox. From the bridge folder, python codex_conversation.py prints its
local URL. The current view shows recent questions, replies, and errors.

Keep the main view simple. List tasks with their current status, then show
the selected task as a chronological conversation. Label each exchange with
who sent it, who received it, the mode (manual, automatic, or delegated),
and the exact model when known. Show Waiting, Working, Answered, Failed, or
Cancelled and the time each transition happened. Make the full question,
shared context, session continuity, artifacts, and technical errors expandable
on the individual request. Group related exchanges by task ID and use the
request ID to distinguish separate runs.

Show the agent's work as an activity timeline under its message. Start with
events the bridge can verify, such as worker started, session resumed, input
opened, check started, check returned a result, and report delivered. A
delegated worker can add visible actions such as files read, authorized tools
used, checks run, and edits prepared. Show a short explanation from the agent
of its approach and conclusions alongside those events. Label model-written
summaries and bridge-observed events separately so a claim can be checked
against the work recorded. A manual answer shows inbox and reply events.

Example timeline for a Kaggle audit

    14:02  Claude assigned Codex to audit the candidate run.
    14:02  Worker started. Opened fold_scores.csv and validation.py.
    14:03  Recomputed the fold average from the supplied scores.
    14:03  Found that the baseline and candidate used different splits.
    14:04  Returned report to the originating Claude session.

Implement the first version from mailbox state changes and a small set of
structured events written as the worker progresses. The existing CLI runner
collects provider output at the end. Live provider activity would require
streaming and parsing the events each CLI exposes. Add those events only where
they convey a useful action or result. Keep raw logs and detailed context
collapsed, sanitize technical output, and keep the page local and read-only.

Conversation memory and recovery

1. Separate unrelated subjects. Start each new subject with a unique topic
   ID and reuse it only when the caller explicitly continues that subject.
   Treat names like “Kaggle review” as display labels. Bind the topic to its
   project and originating session by default, with deliberate continuation
   if another session needs to join. Today the provider-session lookup uses
   only the recipient and task ID, and fallback history matches on task ID.
   Reusing the same hand-written ID in unrelated work can therefore mix
   context. Keep the request ID for tracking one exchange.

2. Show continuity on each request. Display New session, Resumed session,
   or Recovered in a new session. Base the label on what the worker actually
   did. In recovery, show which notes and recent exchanges were carried over
   and that the earlier provider session was unavailable. If a failure leaves
   the outcome of the last turn uncertain, show Failed with that explanation
   and follow the retry policy above. Use Unknown for older records without
   continuity information.

3. Keep a short checkpoint per topic. Save confirmed decisions and why they
   were made, unresolved questions, and references to the relevant request
   IDs or evidence. Let the lead update it after material decisions. Keep it
   separate from the transcript and scope it to the same topic. Today a new
   worker session can be seeded with up to six answered exchanges, capped at
   60,000 characters. On confirmed session loss, seed the new session with
   the checkpoint and recent exchanges from that topic. This preserves older
   decisions while making clear which parts of the discussion were recovered.

4. Test app restart and session loss separately. Open a topic, record a
   decision, restart the initiating app and bridge process, and verify that a
   follow-up resumes the saved session and receives the earlier context.
   Start a separate topic with the same display label and verify isolation.
   Simulate a rejected resume after more than six exchanges and verify that
   recovery carries an older decision and an open question via the checkpoint.
   Simulate a timeout with an uncertain outcome and verify that there is no
   second provider call. The current tests cover storing session IDs,
   follow-up history, and avoiding replay on mailbox restart. The new tests
   should exercise the complete restart and recovery paths.
